## 这份作品集想说明什么

1. **能把一个模糊的痛点，收敛成可交付、可验收的范围。** 从需求定义到「不做什么」的清单，都有明确的判断依据。
2. **能用 AI 把一个想法真正落地成能跑的产品。** 本项目从设计文档、任务拆解、编码到测试全部由「人定架构 + AI 执行」的方式推进（详见第 8 节实录）。
3. **用数据看产品，而不是凭感觉。** 关键行为都在数据层留痕，指标口径先设计、再上线。

## 1. 解决的问题

求职海投的真实成本不在「点投递」这个动作，而在三件被反复消耗的重复劳动：

| 痛点 | 现状 | 这个产品的做法 |
|---|---|---|
| **岗位筛选靠肉眼** | 一天手动翻几百条岗位；硬性条件（城市 / 每周到岗天数 / 实习时长 / 排除词）反复比对 | 规则引擎先过硬性条件，不满足的直接标记「跳过 + 具体原因」，不浪费一次 AI 调用 |
| **一份简历投所有岗** | 投递量大但匹配度低，回复率差 | 按 JD 逐岗重写措辞与量化成果，**保留真实经历、禁止虚构** |
| **投递本身耗时** | 每个岗位重复「进详情 → 填求职状态 → 选附件 → 提交」 | 自动完成全部前置步骤，停在提交之前，用户点一次确认 |

产品判断的前提是：**求职行为的瓶颈是"重复决策"，不是"缺少自动化"。** 所以这个工具做的是把重复决策批量化、把最终决策留给人。

## 2. 功能一览

| 模块 | 能力 |
|---|---|
| **简历** | PDF 上传 → 本地提取文本 → 模型结构化（基本信息 / 教育 / 经历 / 项目 / 技能）→ 人工修正入库；支持按求职方向保存多份简历 |
| **目标** | 岗位关键词（多关键词）、城市多选、行业、公司规模多档、每周到岗天数、实习时长下限、排除词、匹配分数阈值、30 天内不重复投递开关 |
| **检索** | 驱动真实浏览器会话按关键词与城市检索岗位，逐岗抓取 JD 正文 |
| **匹配** | 硬性条件规则先行 → 通过者由模型打分（0–100）+ 一句理由 + 硬性不符项标注 |
| **改写** | 达标岗位按 JD 重写简历内容 → 本地渲染 PDF（文件名自动带公司 / 岗位）；记录页可对单条记录直接改写、预览后导出 |
| **投递** | 自动填好前置项，停在提交前 → 用户确认后提交；支持人工逐岗确认与自动两种模式 |
| **记录** | 已投递 / 失败 / 跳过 / 待人工 全量留痕 + 具体原因，可导出 CSV 做分析 |
| **历史** | 历次任务的可回溯记录与报告导出 |
| **设置** | 模型服务与 Key、运行参数、隐私声明 |

界面分为 **简历 / 目标 / 任务 / 记录 / 历史 / 设置** 六个工作区。

## 3. 产品设计取舍（含"明确不做"清单）

产品形态的价值，一大半来自**选择不做什么**。以下是刻意的取舍：

1. **半自动铁律：提交动作必须由人确认。** 自动化止步于提交按钮之前。*取舍*：牺牲一部分「全自动」的爽感，换取账号安全与责任边界清晰——把批量自动提交的风险集中在用户账号上是不可接受的。
2. **失败降级为「待人工」，不做重试轰炸。** 页面结构变化、验证码、登录失效一律暂停并把控制权交还用户。*取舍*：单次任务完成率下降，但避免了「失败 → 重试 → 触发风控」的连锁反应。
3. **不提供验证码绕过能力。** 遇到验证码整个任务暂停，提示用户手动处理。这是产品红线，不是待办项。
4. **站点差异集中在一层。** 平台适配层是唯一与页面结构耦合的地方，站点改版只改一处；配套离线页面样例做集成测试，改版可以离线复现、不依赖线上环境。
5. **数据只落本地。** 简历与投递记录存本地数据库，仅在做解析 / 匹配 / 改写时发送给用户自己配置的模型服务（界面已声明）。

**明确不做（YAGNI，写进设计文档）**：多账号并发、账号体系、HR 消息自动回复、OCR 兜底、薪资字段解析（站点用字体混淆数字，投入产出比不足）、自然语言操作入口。

前四条不是「功能」，而是**风险边界**——它们决定了这个产品能不能被真实用户长期使用，也决定了它上线后需要多少人工兜底。

## 4. 一次任务的完整流程

```
① 上传 PDF 简历 → 本地提取文本 → 模型结构化字段 → 人工修正 → 入库
② 设定目标：关键词 / 城市 / 行业 / 公司规模 / 每周到岗天数 / 实习时长 / 排除词 / 分数阈值 / 去重开关
③ 启动任务 → 拉起真实浏览器会话（复用系统内核 + 独立用户目录，登录态持久化）
④ 按页收集岗位 → 逐岗抓取 JD 正文（与投递错峰，控制请求节奏）
⑤ 匹配：硬性条件规则先行 → 通过者进入模型打分（分数 + 理由 + 硬性不符项）
⑥ 改写：分数达阈值 → 按 JD 重生成简历内容 → 本地渲染 PDF
⑦ 投递：自动填好前置项 → 停在提交之前 → 用户确认 → 提交
⑧ 记录：成功 / 失败 / 跳过 / 待人工 + 原因，可导出 CSV
```

## 5. 从运营视角看：我会怎么衡量它

上线前先定指标口径，而不是上线后找数据。这个产品**不需要额外埋点**——关键行为已经在数据层落库（任务、岗位、投递记录三张表都有状态与原因字段）。

| 指标 | 口径 | 为什么看它 | 数据来源 |
|---|---|---|---|
| **首次上手成功率** | 新用户中「上传简历 → 设定目标 → 跑完第一次任务」的占比 | 衡量产品是否能在没有指导下被独立使用 | 任务与简历记录 |
| **AI 能力调用率** | 进入打分的岗位数 ÷ 抓取到的岗位数 | 规则过滤是否过紧、AI 的价值有没有被真正用上 | 岗位状态流转 |
| **任务健康度分布** | 已投递 / 跳过 / 失败 / 待人工 各占比 | 一条曲线就能看出问题出在筛选、改写还是投递环节 | 记录页 + 导出 CSV |
| **失败原因 Top N** | 按原因聚合失败与跳过 | 定位是产品问题、站点改版还是用户配置问题 | 原因字段（已落库） |
| **待人工占比** | 需人工接管的岗位占比 | 站点结构变化的「适配健康度」预警指标 | 岗位状态 |
| **人工耗时收益** | 单任务总耗时 vs 手动投递基线 | 产品的核心价值主张是否成立 | 任务时长 + 手动基线 |

**指标 → 动作**：失败原因集中在投递环节 → 优先修适配层；AI 调用率过低 → 放宽规则阈值或优化筛选规则；待人工占比上升 → 站点改版预警，触发适配更新。指标不是为了汇报，是为了决定下一步做什么。

## 6. 技术架构与选型

```
src/
├── main/                      主进程
│   ├── adapters/              平台适配层（接口 + 实现 + 本地样例实现，新增平台只加一个目录）
│   ├── ai/client.ts           模型调用封装（超时 / 中止 / 重试）
│   ├── resume/parse.ts        PDF → 文本 → 结构化字段
│   ├── matcher/engine.ts      规则过滤 + 打分
│   ├── tailor/                按 JD 改写 + 本地 PDF 渲染
│   ├── scheduler/run.ts       任务状态机（节奏控制 + 暂停点 + 断点续跑）
│   ├── browser/pool.ts        浏览器会话与登录态
│   └── db.ts / ipc.ts         数据层 + 类型校验的 IPC
├── preload/                   白名单桥
├── renderer/                  React 界面（六个工作区）
└── shared/                    主渲染共享的类型与纯函数
```

| 选型 | 理由 |
|---|---|
| Electron + React + TypeScript | 桌面端需要真实浏览器会话与本地文件能力；TypeScript 保证主进程 / 渲染层契约一致 |
| esbuild | 构建速度优先；主 / 预加载 / 渲染三端统一打包 |
| jest | 核心逻辑（匹配规则、节奏控制、状态流转、解析）全部可脱离界面单测 |
| better-sqlite3 | 本地单机数据的同步读写，部署零依赖 |
| 复用系统浏览器内核 | 环境更真实、安装包更小；无内核时回退内置内核，保证「不挑电脑」 |
| TypeBox 校验 IPC | 渲染层无法构造非法请求——界面 Bug 不会升级成数据损坏 |

**架构上最值得说的一件事**：平台适配层是抽象出来的（接口 + 两种实现 + 可替换注册表）。新增平台的标准动作是「加一个适配器目录」，界面与调度逻辑不动——这是为「从 1 个平台扩到 4 个平台」提前付的成本，后来证明是省时间的决定。

## 8. AI 协作实录：我实际用的提示词（整理版）

这个项目全程用「我定架构与验收，AI 做落地」的方式推进。以下是其中几段真实使用的提示词（整理后的表达版），以及它们为什么有效。

### 8.1 我的四个固定动作

| 动作 | 做法 | 解决的问题 |
|---|---|---|
| **先定义问题，不接方案** | 需求进来先还原「谁在什么场景下卡住了」，禁止直接进入实现 | 避免做出正确但没人用的功能 |
| **给约束和判据，不给形容词** | 用「不许新增依赖」「测试全绿才提交」「验收标准是 XX」替代「做好一点」 | 让 AI 的产出可验证，而不是可解释 |
| **把执行权和验收权分开** | 无风险的执行授权给 AI，功能验收权始终在人 | 既拿到速度，又不丢质量关口 |
| **每批次留痕** | 偏离计划的取舍都记录「为什么这么定 + 判断错了的代价」 | 让项目几个月后还能被自己接手 |

### 8.2 提示词实例

**① 把「使用感受」翻译成可复现的需求**

> 人工模式下我设置的是「本轮推荐 10 个岗位」，但任务页实际推来了 20 多条。它不算功能缺陷，但会让用户怀疑"我设的参数到底有没有生效"。请先定位根因：是参数没进流水线，还是候选池没有按用户选择收敛？修复后补一条测试把这个行为锁住。

*结构*：可复现现象 → 影响的业务含义（用户信任）→ 给出归因方向（两个假设）→ 要求测试锁行为。
*效果*：问题从「观感不好」变成了一条可验证、可回归的缺陷。

**② 让 AI 先做能力盘点，而不是直接写代码**

> 先不要动代码。请以产品负责人的视角回答三件事：这个版本现在的完整能力边界是什么、有哪些缺口、哪些地方会在真实使用中掉链子。用户群不需要很大，但要是被现有工具忽略掉的那部分真实需求。最后按「影响面 × 修复成本」排序给我。

*结构*：明确禁止直接实现 → 指定角色与视角 → 三个固定问题 → 指定排序口径。
*效果*：产出的是优先级清单，不是一堆代码。

**③ 一次给三个模块，但先讲清依赖**

> 我想加三块能力，请先判断依赖顺序再动手：① 简历库按求职方向存多份（运营 / 销售 / 技术各一份），投递时按方向自动匹配；② 匹配环节要真正读 JD 正文，而不只是比岗位名称——很多岗位名称不同但要求一样（比如 B 端销售和渠道运营），只比标题会漏掉机会；③ 站点的页面结构会变，抓取逻辑要能容忍变化并给出明确失败提示，不要静默丢数据。

*结构*：编号需求 → 每条附「为什么需要」→ 显式要求先定依赖顺序。
*效果*：需求被拆成可独立验收的模块，而不是一个含糊的大需求。

**④ 把「能不能复用」作为架构问题的第一问**

> 我们准备把平台从 1 个扩到 4 个。我的要求是先回答「现有系统能不能平移」：如果适配层设计是对的，新增平台应该只增加一个适配器、不动界面和调度；如果平移动不了，说清是哪一层被写死了，再决定是重构还是新加。

*结构*：目标 → 先立复用假设 → 假设不成立时的追问方向。
*效果*：避免为每个平台复制一套逻辑，也避免无意义的大重构。

**⑤ 用「观感」定义验收标准（运营视角的体验指标）**

> 现在两个问题：启动慢，而且启动前会闪一个黑框。我的验收标准不是「变快了」，而是「看起来像成熟软件」——具体说：有加载界面、有进度反馈、没有黑框；如果必须牺牲一点速度换观感，我选观感。另外请把内存占用按功能拆解给我，我要知道哪一块最重、对应多少磁盘占用。

*结构*：现象 → 用可观察的体验结果定义验收（而非绝对值）→ 明确冲突时的取舍优先级 → 要求可量化拆解。
*效果*：一次拿到「启动提速 + 加载界面 + 内存与体积的分项数据」，而不是模糊的「优化完成」。

**⑥ 把「执行」和「验收」的边界说清楚**

> 这批任务按你的判断直接推进，无风险的操作不需要逐条问我，我会在功能做出来之后统一验收。三条前提：不新增依赖、不改变已经确认过的交互、每次改动后测试必须全绿。

*结构*：授权范围（无风险 = 自主）→ 验收权归人 → 前置红线（约束提前给，不靠事后返工）。
*效果*：协作速度快，且产出始终落在可验收的范围里。

**⑦ 我自己写的「价值预审」角色（元提示词）**

> 你是我的项目价值预审官。在任何项目立项之前，你先只做一件事：判断它是不是自嗨。规则：① 价值判断优先于技术实现，禁止直接进入方案和代码；② 立场客观，不附和我的自我感动；③ 默认前提是市面上大概率已有成熟替代方案，我脑补的需求大多是伪需求。请按「痛点是否真实 / 现有替代方案 / 最小验证成本 / 长期维护成本 / 失败代价」五个维度一次性提问，等我答完再给判断。

*结构*：角色 → 工作原则 → 默认假设 → 固定检查清单。
*效果*：这是我最常用的 prompt 骨架——**先对齐判断标准，再讨论方案**。用它挡掉的伪需求，比它写出的代码更值钱。

### 8.3 这套方法在运营岗位上的迁移

同一套逻辑可以正面迁移到运营工作：**先定义问题与指标口径 → 用约束和小成本实验验证 → 把可自动化的执行交出去 → 用数据回看效果并决定下一步**。区别只在于 AI 写的是代码，还是文案、活动方案、数据口径。我把它当作一套「可复用的做事方式」，而不是一个编程技巧。

## 9. 运行环境与已知限制

**运行环境**：Windows 10 / 11（x64）。首次启动需同意使用协议；模型相关功能需要用户自行配置模型服务的 API Key（用多少付多少，不经过任何中间服务）。报告导出功能需完成设备绑定后才可使用。

**已知限制**：

- 仅支持 Windows。
- 当前以单一招聘平台适配为主，其余平台通过适配层扩展。
- 改写与打分质量取决于所配置的模型能力。
- 简历解析依赖 PDF 文本层，扫描件需手动粘贴文本兜底。
- 界面截图与演示 GIF 整理中。

## 10. 合规边界

- 本工具定位为**个人求职效率辅助**：自动化止于提交之前，投递确认权始终在人。
- 不提供验证码绕过能力，不承诺规避平台规则；请求节奏与上限以「不影响用户账号」为第一约束。
- 适配层针对公开页面结构编写；页面改版即停止工作并明确提示用户，不做对抗式修补。
- 数据全部存本地，仅在做解析 / 匹配 / 改写时发送给用户自行配置的模型服务，产品内已有隐私声明。
